# Tauri Glass Dock — заметки из первого прохода

Конспект решений и грабель, уже пройденных при первой версии этой панели.
Не передоказывать заново — использовать как отправную точку.

## Tailwind v4: регистрация анимаций

`@theme { --animate-<name>: <keyframe-name> <duration> <easing> <iteration>; }` в
`src/index.css` сама генерирует утилиту `animate-<name>`, ровно как `--color-*`
генерирует `bg-*`/`text-*`. `@keyframes` при этом объявляются как обычно, вне блока
`@theme`. Уже сделаны и рабочие: `animate-rgb-glow` (перелив рамки), `animate-led-pulse`
(дыхание индикатора через `currentColor`, чтобы не красить фон и тень отдельно).

Числовые функциональные утилиты (`scale-*`, `opacity-*`, `rotate-*`) в v4 динамические —
`scale-120` работает из коробки, без записи в `@theme`.

## Источник иконок приложений

Для мокапа использовался проект **Dashboard Icons** (`homarr-labs/dashboard-icons`),
паттерн: `https://raw.githubusercontent.com/homarr-labs/dashboard-icons/main/png/<slug>.png`.
Важно: `cdn.jsdelivr.net/gh/homarr-labs/dashboard-icons/...` сейчас у многих иконок отдаёт
ошибку `Package size exceeded 50 MB` (репозиторий перерос лимит jsDelivr на весь GH-пакет) —
`raw.githubusercontent.com` этой проблемы не имеет, т.к. отдаёт файлы по одному.

Для реального приложения (не мокапа) удалённые PNG — временное решение. В финале лучше
доставать нативную иконку установленного приложения на диске пользователя (на macOS —
через `.icns` / `NSWorkspace`, крейт вроде `icns` или системный вызов), либо бандлить
статичный набор внутри приложения — так дизайн не зависит от сети и всегда актуальному
масштабу/DPI. Всегда оборачивать `<img>` в `onError`-fallback (бейдж с инициалами на
`app.color`) — сеть или отсутствующая иконка не должны рендерить битую картинку.

## Прозрачное окно и click-through

- Обёртка на весь экран — `pointer-events-none`; сам видимый pill дока —
  `pointer-events-auto`. Без этого прозрачное always-on-top окно перехватывает клики
  по всему нижнему краю экрана, даже там, где нет самой панели.
- CSS-уровня `pointer-events-none` достаточно для кликов внутри веб-контента, но не
  гарантированно для всех платформенных сценариев (фокус окна, drag снаружи) — держать
  в уме `appWindow.setIgnoreCursorEvents(true/false)` как второй уровень защиты,
  переключаемый по `mouseenter`/`mouseleave` на pill.
- `html, body, #root { background: transparent !important; }` — обязательная строка,
  тонет среди Tailwind preflight и легко теряется при рефакторинге `index.css`.

## Glass-эффект: backdrop-blur — это НЕ vibrancy

`backdrop-filter: blur()` блюрит контент, находящийся позади элемента в том же дереве
веб-страницы. У полностью прозрачного окна позади дока в DOM ничего нет — реальный
рабочий стол рендерится другим процессом ОС, до которого CSS не достаёт. Итог: чисто
CSS-стеклянный док на прозрачном окне НЕ блюрит то, что реально позади него на экране,
только тонирует (`bg-zinc-950/80`) без размытия.

Для настоящего frosted glass — нативный vibrancy: крейт `window-vibrancy`,
`apply_vibrancy(&window, NSVisualEffectMaterial::HudWindow, None, None)` на macOS.
Держать Tailwind `bg-zinc-950/80` как цветовой тонирующий слой ПОВЕРХ vibrancy, не
вместо него.

Подключено во втором проходе (`platform/macos.rs`, `apply_dock_vibrancy`). Материал —
`HudWindow`: это фиксированный (не семантический) материал, он остаётся тёмным
независимо от системного Light/Dark Mode — важно для always-dark Razer-Chroma эстетики.
`Sidebar` — семантический материал, в Light Mode резолвится в светлый/полупрозрачный вид
и вымывает RGB-рамку и `bg-zinc-950/80` тонировку (проверено визуально, см. коммит).

### Corner masking: окно больше пилюли — маскировать нужно blur-view, не contentView

`apply_vibrancy()` всегда растягивает свой `NSVisualEffectView` на весь `bounds()`
переданного view — то есть на весь `NSWindow` (511×111 DIP), а не на видимую CSS-пилюлю
(456×91 DIP, `rounded-[28px]`). Разница между окном и пилюлей — не случайный отступ, это
активный канвас WKWebView под RGB-glow `box-shadow` и будущий hover-magnify/tooltip
overflow (см. `PILL_TOP_RESERVE_PX` / `WINDOW_GLOW_BLEED_PX` в `constants.ts`). Поэтому
здесь нельзя просто повесить `contentView.layer.cornerRadius` + `masksToBounds` на весь
content view, как это обычно делают для frameless-окон — это заодно обрежет WebView и
сломает glow/будущий magnify overflow, а сам blur всё равно останется прямоугольным на
всю ширину/высоту окна (проверено — именно так рендерится, если этот шаг пропустить).

Рабочий рецепт: вызвать `apply_vibrancy(.., radius: Some(28.0))` как обычно (радиус тут
двигает угол ТОЛЬКО у той view, что вернёт функция), затем найти эту view обратно через
`NSView::viewWithTag` по внутреннему тегу крейта (`NS_VIEW_TAG_BLUR_VIEW = 91_376_254` —
не экспортируется, задокументировано константой с explicit-комментарием на файл/версию
крейта) и вручную сжать её `frame` до размеров пилюли (центрировано по X, с отступом
`DOCK_BOTTOM_INSET_DIP` снизу — знак смещения по Y зависит от `contentView.isFlipped()`,
проверять в рантайме, не хардкодить). `setCornerRadius` не зависит от размера — сужение
`frame` после вызова `apply_vibrancy` не портит уже выставленное скругление.

`NSRect`/`NSPoint`/`NSSize` при этом не нужно называть явно (и не нужно тащить
`objc2-foundation` отдельным доп.-зависимостью) — `content_view.bounds()` уже даёт
готовое значение нужного типа, а `origin.x/y` и `size.width/height` — публичные поля,
их можно читать/писать через инференс типа, без явного упоминания структуры.

### Click-through поллер должен знать про скруглённые углы

После маскировки поллер (`start_click_through_poller`) обязан считать «внутри пилюли» по
той же скруглённой форме, а не по прямоугольнику `pill_left/top/right/bottom` — иначе 4
угловых треугольника снаружи видимой скруглённой пилюли, но внутри её bounding box, будут
ошибочно перехватывать клики. Решение — `in_rounded_rect()`: быстрый reject по внешнему
прямоугольнику, затем проверка расстояния до центра ближайшего угла (`radius²`) только
если точка попала в угловую r×r область; в противном случае — точка на прямом крае,
сразу `true`. `radius` скейлится так же, как `pill_w`/`pill_h`/`inset` (`* scale`), т.к.
`outer_position()`/`outer_size()` у Tauri в физических пикселях, а DIP-константы — нет.

### Клики по иконкам: CGEventTap, не сэмплирование в поллере

Поллер (`start_click_through_poller`) отвечает только за непрерывное состояние:
`set_ignore_cursor_events`, `dock-hover`, `dock-cursor`. Клики — отдельный
`CGEventTap` на `LeftMouseDown` (`start_dock_click_tap`): event-driven перехват
на HID-уровне, надёжен для коротких тапов трекпада и для случаев, когда
`NSVisualEffectView` проглатывает `mouseDown` до WKWebView.

На фронте единственный обработчик toggle — `listen("dock-click")` в
`DockPanel.tsx`; у `DockIcon` нет собственного `onClick` (два источника давали
double-toggle). Tap — pass-through, событие не блокируется. Требует
Accessibility / Input Monitoring в System Settings; при неудачном создании tap
клики по иконкам не работают, hover/click-through от поллера остаются.

#### Почему не `NSEvent.addLocalMonitorForEventsMatchingMask` вместо `CGEventTap`

Пересмотрено при добавлении hover-magnify — вопрос был явно поставлен, чтобы не
превращать выбор `CGEventTap` в молчаливое умолчание. Локальный монитор
(`addLocalMonitorForEventsMatchingMask`, без Input Monitoring) обычно и есть
стандартное лекарство именно от исходной проблемы — `NSVisualEffectView`,
глотающего `mouseDown` до React: монитор перехватывает событие на уровне
`NSApplication.sendEvent`, до того как per-view hit-test дойдёт до vibrancy-view
и проглотит его. Соседний риск — "первый клик по неактивному/некиевому окну
только активирует его, не доходя до вью" — тоже уже снят: в `tauri.conf.json`
стоит `"acceptFirstMouse": true`, так что первый клик по неактивному доку и так
доставляется во вью, а не тратится только на активацию.

Реальная причина не менять — гонка с `set_ignore_cursor_events` в
`start_click_through_poller`. Пока курсор снаружи пилюли, окно всегда в режиме
`ignoresMouseEvents(true)` — клик в этот момент вообще не доходит до
`NSApplication`/AppKit-диспетчеризации, WindowServer молча отдаёт его тому, что
находится за окном; локальный монитор в принципе не может увидеть событие,
которого приложению не доставили. Флаг снимает только поллер, раз в
`CLICK_POLL_MS` (сейчас 50 мс) — то есть после того, как курсор визуально уже
на пилюле, есть окно до 50 мс, где клик всё ещё проваливается сквозь окно.
Короткий тап трекпада ("навёл и сразу тыкнул", без задержки на движение) —
ровно тот случай, что уже отмечен выше как причина выбора HID-уровня, — попадает
именно в эту гонку. `CGEventTap` перехватывает на HID-уровне ДО любой проверки
`ignoresMouseEvents`, поэтому от неё не зависит.

Итог: `CGEventTap` остаётся. Понижение `CLICK_POLL_MS` сужает окно гонки, но не
убирает его целиком — если она когда-нибудь станет ощутимой на практике, это
отдельная задача (частота поллинга или пересмотр архитектуры), а не повод тихо
подменить один механизм другим по ходу несвязанной правки.

### Частота поллинга: sleep-бюджет, не busy-loop

`CLICK_POLL_MS` — это `std::thread::sleep` между итерациями, не busy-loop: поток спит,
затем делает несколько дешёвых вызовов (пара геттеров Tauri + позиция курсора)
и снова засыпает. Сейчас **50 ms** (20 Гц) — достаточно для границы click-through
и hover/tooltip. Раньше здесь стояла пометка «поднятие до 10 ms (100 Гц) —
отдельное решение под будущий hover-magnify (`dock-cursor`)» — она не
подтвердилась: реализованный magnify берёт позицию курсора из нативного
`onMouseMove` в React (см. секцию про hover-magnify ниже), а не из `dock-cursor`,
поэтому частота ЭТОГО поллера на плавность magnify не влияет и поднимать её
для magnify не нужно; `dock-cursor` остался только вспомогательным сигналом для
click-through решений на Rust-стороне. Измерено на живом сборе (`ps -o pid,time` до/после,
Δ CPU time / Δ wall time): весь процесс (WebView + непрерывные CSS-анимации RGB-glow и
LED-pulse + vibrancy-композитинг + поллер) в простое — около 7% одного ядра; из них сам
поллер на 100 Гц даёт всего ~2.5 п.п. сверх бейзлайна без поллера (~4.5%, чисто
WebView-анимации) — то есть основная база CPU-нагрузки в покое не от поллера, а от
непрерывных CSS keyframe-анимаций рамки/LED, которые в любом случае работают всегда.

## LED-индикатор запущенного приложения

Цвет индикатора и его свечения берутся из ОДНОГО класса на родителе (`text-<color>-400`),
а сам индикатор использует `bg-current` (фон) и `box-shadow: currentColor` внутри
`@keyframes led-pulse` (свечение) — так не нужно синхронизировать два цвета вручную при
добавлении нового приложения в mock-данные, достаточно одного поля `color`.

## Hover-magnify в стиле macOS — отдельная фаза, не путать с обычным hover

Настоящий Dock-magnify — не `:hover { scale: 1.2 }` на одной иконке. Это непрерывная
функция расстояния курсора до КАЖДОЙ иконки в ряду (соседи тоже увеличиваются, по
затухающей кривой), пересчитываемая на каждый `mousemove`. Типичная реализация —
Framer Motion `useMotionValue` (позиция курсора) + `useTransform` на каждую иконку
(расстояние → scale), а не набор дискретных CSS-брейкпоинтов. Важно для
производительности: анимировать только `transform`/`scale` (не layout-свойства), при
необходимости троттлить `mousemove` через `requestAnimationFrame`. Планировать и
тестировать как отдельный проход поверх уже стабильной статичной геометрии панели —
не смешивать с первым проходом по вёрстке/стеклу/RGB-рамке.

### Как реализовано (третий проход)

Сделано именно `scale`-only, без реального reflow дока — окно/пилюля уже были
зафиксированы в 511×111 / 456×91 DIP с запасом ровно под `MAGNIFY_MAX_SCALE`
(см. `PILL_TOP_RESERVE_PX` / `WINDOW_WIDTH_DIP` в `constants.ts`), поэтому
увеличенная иконка может визуально слегка перекрыть соседей на пике — осознанный
компромисс, не баг.

- **Источник курсора — гибрид: нативный `onMouseMove` + `dock-cursor` как
  fallback.** Когда окно в фокусе, WKWebView получает `mousemove` на полной
  частоте — этого достаточно для плавного magnify. Когда окно **не** в фокусе,
  DOM `mousemove` не приходит (даже после снятия `ignoreCursorEvents` поллером)
  — тогда magnify и тултип снова кормятся из `dock-cursor` (20 Гц, чуть
  ступенчато, но работает). Фронт игнорирует `dock-cursor`, если за последние
  ~80 ms был нативный `onMouseMove`, чтобы не дёргать анимацию при фокусе.
- **Кривая** — `useMotionValue<number>` на X курсора (`Infinity` = курсора нет)
  → в каждой `DockIcon` свой `useTransform` считает расстояние до
  `getBoundingClientRect()` собственного узла → второй `useTransform` мапит
  дистанцию `[-MAGNIFY_INFLUENCE_RADIUS_PX, 0, MAGNIFY_INFLUENCE_RADIUS_PX]` в
  scale `[1, MAGNIFY_MAX_SCALE, 1]` → `useSpring` сверху для физики/сглаживания.
  Анимируется только `scale` через `motion.img`/`motion.div style={{ scale }}`;
  старый Tailwind `transition-transform` снят с иконки — CSS-transition поверх
  Motion-управляемого inline-стиля той же схемы (`transform`) даёт видимую
  "борьбу"/лаг двух аниматоров за одно свойство.
- **LED-индикатор запущенного приложения magnify-scale не получает** — только
  собственный discrete on/off переход активности. У настоящего macOS Dock точка
  под иконкой тоже не растёт вместе с иконкой; вдобавок наложение
  Motion-инлайн-`scale` и Tailwind-класса `scale-0` (on/off) реально
  конфликтовало бы — inline-стиль всегда бы перебивал класс.
- **Клик по увеличенной иконке.** `pill_cursor_at_screen()` на Rust-стороне
  остаётся грубым статичным прямоугольником всей пилюли (с запасом под
  magnify) — синхронизировать точный hit-box с Rust на каждый кадр анимации
  через IPC не нужно (60 fps через границу процессов — лишняя нагрузка).
  `getBoundingClientRect()` уже возвращает текущий, отмасштабированный
  bounding box (CSS `transform` влияет на него), так что `hitTestIcon()` во
  фронте автоматически видит выросшую область. Единственное необходимое
  усиление — при пересечении рамок двух соседних иконок (увеличенная
  визуально заходит на территорию соседа) выбирать ту, чей центр ближе к точке
  клика, а не первую по порядку в `Map` — иначе на границе можно было бы
  промахнуться на соседнюю.
- Троттлинг `onMouseMove` через `requestAnimationFrame` не добавлен — не
  потребовался: Framer Motion сам батчит запись стилей через свой rAF-шедулер,
  а React-стейт (`hoveredIconId`, для тултипа) перерендеривается только при
  реальной смене наведённой иконки, не на каждый пиксель движения. Добавить
  троттлинг — тривиальная правка, если профилирование когда-нибудь покажет
  просадку, но заранее это не сделано намеренно.
- **Динамическая высота пилюли — намеренно НЕ делаем.** CSS-пилюля и vibrancy
  всегда фиксированы на `PILL_HEIGHT_PX` (91 DIP). Magnify — только
  `transform: scale()` с `origin-bottom`: увеличенные иконки и тултип
  перекрывают прозрачный `PILL_TOP_RESERVE` над пилюлей, не растягивая
  `bg-zinc-950/80`. Полный resize окна на hover тоже не делаем. Rust-поллер
  при `dock_hovered` расширяет hit-test до `PILL_HEIGHT_HOVER_DIP`, чтобы
  курсор над увеличенной иконкой не выпадал из click-capture.

### `centerX` инвалидация по входу в hover-сессию, не только `ResizeObserver`

`ResizeObserver` в `DockIcon` реагирует только на изменение размера
наблюдаемого узла, не на его позицию — сценарий "геометрия сдвинулась (layout
поменялся, например `PILL_TOP_RESERVE`), а размер иконки не изменился" им не
покрывается. Добавлен второй, дешёвый источник инвалидации: `DockPanel`
хранит `hoverSessionId` (счётчик), инкрементируемый в момент начала каждой
hover-сессии — нативный `onMouseEnter` на пилюле и переход `dock-hover` →
`true` от Rust-поллера (тот эмиттит это событие только на транзишене, то есть
уже один раз на "вход", без дополнительных проверок на фронте). `DockIcon`
получает `hoverSessionId` пропом и держит второй `useLayoutEffect`,
пересчитывающий `centerX` при каждом его изменении — вызовов не больше одного
на hover-сессию, `mousemove` не участвует.

## Реальный process-monitoring и нативные иконки (четвёртый проход)

Мокнутые `isActive` (React-стейт, тоггл по клику) и remote PNG-иконки
(Dashboard Icons) заменены на данные `NSWorkspace` для того же
фиксированного списка из 6 приложений — конфиг (`id`/`name`/`bundleId`/
`color`) переехал в Rust (`commands/apps.rs::APPS`) как единственный
источник правды; фронт больше ничего не мокает и не мутирует локально.

### Event-driven, не поллинг

`platform::macos::start_apps_monitoring` берёт один снимок
`NSWorkspace.sharedWorkspace().runningApplications()` при старте для
начального состояния, затем подписывается на
`NSWorkspaceDidLaunchApplicationNotification` /
`NSWorkspaceDidTerminateApplicationNotification` через
`NSWorkspace.notificationCenter().addObserverForName_object_queue_usingBlock`
(крейт `block2::RcBlock` для блока-замыкания; `queue: None` — блок
выполняется синхронно на потоке, отправившем уведомление, то есть на главном
потоке приложения, где и крутится Tauri/AppKit run loop). Из `userInfo`
notification'а по ключу `NSWorkspaceApplicationKey` достаётся
`NSRunningApplication`, её `bundleIdentifier()` сверяется с 6 отслеживаемыми
ID — обновление состояния инкрементальное, полного пересканирования списка
на каждое событие нет. После этого во фронт эмиттится `apps-state-changed` с
полным снапшотом всех 6 приложений (проще, чем дельты, и снапшот всё равно
маленький).

Отдельная гонка "событие пришло раньше, чем фронт подписался" закрыта не
буферизацией на Rust-стороне, а простым pull-командой при монтировании:
`get_apps_snapshot` отдаёт текущее состояние по явному запросу, `listen`
на `apps-state-changed` подписывается следом и ловит только последующие
изменения.

### Почему `NSRunningApplication` НЕ хранится живым в общем состоянии

Ожидаемый по умолчанию подход — держать карту `bundleId -> NSRunningApplication`
в Rust-стейте, обновляемую по тем же двум уведомлениям, чтобы клик по уже
запущенному приложению активировал сохранённый инстанс напрямую. От этого
осознанно отказались: AppKit-объекты в общем случае не `Send`/`Sync` между
потоками, а `#[tauri::command]`-обработчики выполняются в пуле потоков
Tauri, отдельном от главного потока, на котором живут `NSWorkspace`-
уведомления и вообще все AppKit-вызовы. Хранить `Retained<NSRunningApplication>`
в структуре, которую потом читают из другого потока — это либо не
скомпилируется, либо небезопасно.

Вместо этого `AppsState` хранит только простые данные: `Mutex<HashMap<bundleId,
bool>>` (running) и `Mutex<HashMap<bundleId, Option<String>>>` (кэш иконок) —
оба безопасно читаются/пишутся с любого потока. Активация по клику
(`activate_or_launch_app`) синхронно и заново резолвит текущий
`NSRunningApplication` через `NSRunningApplication::runningApplicationsWithBundleIdentifier`
**на главном потоке** (диспетчеризация через `AppHandle::run_on_main_thread`
— команда сама выполняется в threadpool, а любые AppKit-вызовы внутри неё
обязаны уйти на главный поток). Функционально результат тот же — активируется
существующий инстанс, второй не запускается — просто без переноса живого
указателя между потоками. Клик — редкое, явное действие пользователя, а не
поллинг, так что лишний lookup по bundle ID на клик не стоит того риска.

### Нативные иконки: `NSImage` → `CGImage` → `NSBitmapImageRep` → PNG

Путь до `.app` резолвится по bundle ID через
`NSWorkspace.URLForApplicationWithBundleIdentifier`, иконка — через
`NSWorkspace.iconForFile(path)` (не парсинг `.icns`/`Info.plist` вручную).
`NSImage` в используемой версии `objc2-app-kit` (0.3.2) не даёт прямого
`TIFFRepresentation`/PNG-метода — рабочий путь оказался через
`CGImage`: `NSImage.CGImageForProposedRect_context_hints(...)` →
`NSBitmapImageRep::initWithCGImage(...)` →
`representationUsingType_properties(NSBitmapImageFileType::PNG, ..)` → байты
`NSData` (`.to_vec()`). Из байт собирается `data:image/png;base64,...` через
крейт `base64` (`Engine::encode` на `base64::engine::general_purpose::STANDARD`).
Изначально здесь стоял рукописный RFC 4648 энкодер (десяток строк) — заменён
на стабилизационном проходе: баг на границе паддинга (хвост данных, не
кратный 3 байтам) не роняет сборку и не кидает ошибку, а тихо портит
конкретные иконки конкретного размера — риск, который не стоит точечной
экономии одной cargo-зависимости (см. явное исключение в `CLAUDE.md`).
Результат кэшируется в `AppsState.icons` по bundle ID один раз при старте —
не резолвится заново на каждый рендер или уведомление (кроме повторной
попытки при позднем `didLaunch`, см. ниже). `None` (не установлено / не
резолвилось) — фронт показывает тот же fallback-бейдж, что и при `onError`
на `<img>`.

Новые cargo-зависимости под `cfg(target_os = "macos")`: `objc2-foundation`
(была только транзитивной — теперь явная, для `NSNotification`/`NSString`/
`NSURL`/`NSArray`/`NSData`/`NSDictionary`), `block2` (была транзитивной через
`objc2-app-kit` — теперь явная), `objc2-core-graphics` (новая, только ради
типа `CGImage` — фича `CGImage`), `base64` (новая, добавлена на
стабилизационном проходе — см. явное исключение в `CLAUDE.md`). На
`objc2-app-kit` добавлены фичи `NSWorkspace`, `NSRunningApplication`,
`NSApplication`, `NSImage`, `NSImageRep`, `NSBitmapImageRep`.

### Разрешения

`runningApplications()` и подписка на `didLaunch`/`didTerminate` — полностью
публичный API, не требующий privacy-разрешений (в отличие от предыдущего
этапа с `CGEventTap`/Input Monitoring). Если по ходу дальнейшей работы
всплывёт системный запрос нового разрешения на этом пути — это сигнал, что
выбран не тот API, а не повод добавить разрешение молча.

### Bundle ID: проверено, не угадано

`com.hnc.Discord`, `com.valvesoftware.steam`, `com.spotify.client`,
`com.obsproject.obs-studio` — сверены `mdls -name kMDItemCFBundleIdentifier`
на установленных копиях. `com.mojang.minecraftlauncher` и
`com.epicgames.EpicGamesLauncher` изначально были сверены только по
нескольким независимым источникам в вебе (ни один лаунчер не был установлен
на машине первого прохода) — на стабилизационном проходе оба доустановлены
через Homebrew cask (`brew install --cask minecraft epic-games`) и сверены
`mdls`-ом на месте: оба совпали со значениями, уже стоявшими в `APPS`,
изменений не потребовалось. `mdls` на свежеустановленных касках первый раз
вернул `(null)` — Spotlight ещё не проиндексировал бандл; `mdimport
<path>.app` (или пара секунд ожидания) решает это, `Info.plist`
(`CFBundleIdentifier`) через `PlistBuddy` — не зависящая от индексации
альтернатива на случай похожей заминки в будущем.

## Трей-иконка и окно настроек (пятый проход)

### Template-иконка без внешних инструментов

Окружение первого прохода не содержало ни `PIL`, ни `rsvg-convert`, ни
`imagemagick` — только `sips` (не умеет рисовать примитивы, только
конвертировать/ресайзить готовые растры). Иконка трея (44×44,
чёрная заливка + альфа-канал, три скруглённых квадрата) собрана
раскодированием напрямую по спецификации PNG: буфер пикселей заполняется
аналитическим тестом «внутри скруглённого прямоугольника» с ручным
supersampling (4×4) для сглаживания краёв, затем упаковывается в
`IHDR`/`IDAT`/`IEND` через стандартные `struct`+`zlib` из Python stdlib —
без единой сторонней библиотеки. `icon_as_template(true)` на
`TrayIconBuilder` красит её под текущий Light/Dark Mode меню-бара; цветной
PNG в этом режиме смотрелся бы грязно (см. также заметку про `HudWindow` в
разделе про vibrancy — тот же принцип «не мешать системному тонированию»).

### Клик по трею → окно настроек: `TrayIconEvent::Click` + ленивое окно

`TrayIconBuilder::show_menu_on_left_click(false)` освобождает левый клик под
кастомное действие (`open_settings_window`), правый клик показывает меню
(`Quit`) штатным поведением библиотеки — не нужно вручную различать кнопки
для меню. Окно настроек создаётся лениво при первом клике
(`WebviewWindowBuilder::new` внутри обработчика, не в `tauri.conf.json`/
`setup()`) и переиспользуется (`show()`+`set_focus()`) при повторных кликах,
если `app.get_webview_window("settings")` уже что-то возвращает — пользователь,
ни разу не открывший настройки, не платит вторым WebView.

`ActivationPolicy::Accessory` не потребовал никакой дополнительной
донастройки фокуса: `show()`+`set_focus()` на уже существующем окне и обычный
`.build()` для нового — оба варианта надёжно выводят окно настроек на
передний план и в фокус без ручного `app.activate()` (проверено вживую
синтетическим HID-кликом, см. ниже).

### Живая проверка клика по трею: обязателен настоящий HID-клик, не AX-эмуляция

Клик по трею проверялся не мышью тестировщика, а автоматизацией — и здесь
есть ловушка: клик через Accessibility API (`System Events` →
`click menu bar item ...`, синтетический `AXPress`) **не долетает** до
обработчика `on_tray_icon_event` крейта `tray-icon` — он ловит клики на
уровне нативных `NSStatusItem`/mouse-событий, а не через accessibility
action. Рабочая проверка — синтетическое HID-событие через
`CGEvent(mouseEventSource:mouseType:mouseCursorPosition:mouseButton:)` +
`.post(tap: .cghidEventTap)` (маленький Swift-скрипт, `swiftc`+запуск),
координаты клика — из `position`/`size` того же `AXMenuBarItem`
(`System Events` корректно репортит геометрию, даже если сам `click`-verb
не работает). Такой клик неотличим от настоящего аппаратного и надёжно
триггерит открытие окна — этим подтверждён весь путь `TrayIconEvent::Click`
→ `open_settings_window` → фокус окна.

То же самое верно и для тумблеров/чекбоксов **внутри** WKWebView:
`role="switch"` на кастомном `<button>` в WebKit иногда не прокидывает
`AXPress` в реальный DOM `click` (плавающий баг, не воспроизводится
стабильно) — если автоматической проверке нужно понадёжнее, тот же приём
(реальный `CGEvent` по координатам элемента, а не accessibility-`click`)
надёжнее, чем UI-скриптинг через `System Events`.

### Настройки: `dock-settings.json` рядом с `dock-apps.json`, общий `persistence.rs`

Атомарная запись (`.tmp` → `rename`) и путь `app_data_dir()/<file>.json`
были продублированы между `apps.rs` и новым `settings.rs` один в один —
вынесены в `persistence.rs` (`app_data_file`, `write_json_atomic`). Логика
чтения/reseed при битом файле осталась в каждом домене отдельно — это
единственная часть, которая по-настоящему отличается (у `apps.rs` свой лог
о повреждении), унифицировать её не стали.

## Проверено на пересечении фич (QA-проход, 2026-07-08, PROMPT_17)

Живая проверка комбинаций на всех 4 позициях × размерах 44/56/72 (скриншоты,
HID-клики/драги, замеры окна через CGWindowList). Что подтверждено рабочим и
что починено — чтобы следующий проход не перепроверял то же самое:

- **Drag-reorder × bounce × magnify** — без визуального конфликта: bounce
  (`y` на внутреннем узле) и drag-трансформ `Reorder.Item` (внешний узел)
  компонуются, magnify на время драга/settle подавлен (механика `6a9c3e8`
  держится). Починен найденный race: финальный `onReorder` и `onDragEnd`
  могут прийти в один тик, а `commitReorder` читал `itemsRef`, обновляемый
  эффектом — порядок персистился «на один свап позади». Теперь
  `reorderItems` пишет в ref синхронно (`useDockApps.ts`).
- **Add/remove reflow на Left/Right/Top** — вставка/удаление разделителя и
  апп-ростер меняют длину строго вдоль правильной оси, окно перецентровано
  тем же вызовом (например, Left: +13.3 DIP длины при вставке, y сдвинулся
  на половину — центрирование сохранено). Гладко на всех позициях.
- **Геометрия/hit-test после закрытия бокового меню** — окно возвращается к
  размеру пилюли, клик в зону бывшего меню снова проходит сквозь
  (`set_menu_overlay(false)` → shrink → `dock-menu-overlay-closed` →
  геометрия/vibrancy пересинхронизированы). Для стандартного меню окно
  вообще не растёт: `pill_far_reserve` уже вмещает 214 DIP меню.
- **Позиция × размер иконок** — слайдер/пресеты живьём на Left/Right/Top:
  спринг, vibrancy и hit-test следуют за DOM. Починены три бага этой связки:
  1. **Cold start с непересжатым размером/позицией** — первый рендер всегда
     монтировался с дефолтами (56/bottom), а `jump()` после гидрации не
     доходил до DOM (WKWebView может десятки секунд не давать кадров
     свежепоказанному нефокусному окну). Теперь `DockPanel` рендерит пилюлю
     только после гидрации настроек — все Motion-стили пишутся корректными
     первым же коммитом React (`HydratedDockPanel`).
  2. **`gap` через Framer Motion** — `gap` нет в px-append карте motion-dom
     (`numberValueTypes`), числовые обновления после маунта CSS молча
     игнорирует (React на маунте дописывает `px`, Framer — нет). Все
     motion-гэпы теперь строки `"<n>px"`. Симптом был: после смены размера
     DOM-пилюля расходилась с Rust-формулой на ~17px (10 гэпов × Δ).
  3. **`icon_size_changed` в `apply_dock_settings` не срабатывал** —
     `sync_icon_size_preview` писал превью прямо в `settings.icon_size_px`,
     и к моменту коммита сравнение видело равные значения →
     `refresh_dock_icons` пропускался. Превью вынесено в отдельное поле
     `SettingsState.preview_icon_size_px` (override в
     `current_icon_size_dip`).
- **Deadlock в `refresh_dock_icons`** (вскрылся после фикса №3 — раньше путь
  просто не исполнялся): функция держала guard `entries` и внутри вызывала
  `icons_snapshot()`, который лочит `entries` повторно — main thread вставал
  навсегда (оба webview «замерзают», клики мимо, симптомы похожи на
  suspension). Диагностирован через `sample` (стек:
  `refresh_dock_icons → icons_snapshot → psynch_mutexwait`). Теперь
  `entries_snapshot()` (клон) вместо guard. Урок: `std::sync::Mutex`
  нереентерабелен — не вызывать методы `AppsState`, беря его же локи, пока
  держишь guard.
- **Позиция × reorder-drag** — реально перетаскивалось на Left (axis="y",
  вверх и вниз, с overshoot) — порядок и персист корректны.
- **Позиция × вставка разделителя** — вставка через меню идёт по порядку
  списка (ось правильная автоматически); подписи пунктов теперь
  ориентационные («сверху/снизу» на вертикальном доке). Финдер-дроп тоже
  починен: `resolveInsertIndex`/insert-маркер считали только X — на
  вертикальном доке любой дроп падал в индекс 0, маркер рисовался поперёк
  не той оси; теперь ось берётся из `orientation.magnifyAxis`.
- **Размер иконок × разделители** — слот 7 DIP и толщина линии фиксированы
  (осознанно, зеркалится в Rust), длина линии скейлится (ratio 0.6).
  Починен дрейф базовой линии: `mb-3`/`gap-2` были фиксированными, а
  формула толщины использует скейленный `iconLedGapPx` — на 44/72 разделитель
  и LED-полоса уезжали на 1–3px от низа иконок. Теперь и отступ дивайдера, и
  gap иконка↔LED (DockIcon + колонка шестерёнки) берутся из `getSizeMetrics`.
- **LED auto-color × размер × позиция** — кэш акцентов стабилен (сэмпл идёт
  с крупнейшего битмап-репа NSImage, от export-размера не зависит);
  цвета не сбрасываются при сменах размера/позиции подряд; после фикса №3
  `refresh_dock_icons` реально перерастеризует PNG при смене размера.
  Замечено отдельно: у некоторых системных апп (Voice Memos на macOS 15)
  `NSWorkspaceDidTerminateApplicationNotification` не постится вовсе
  (launch приходит, terminate — нет; для Notes/App Store всё парно) — LED
  может остаться гореть до перезапуска/следующего события. Это ограничение
  macOS-уведомлений, не регрессия дока; чинить (поллинг `isTerminated` или
  KVO на `NSRunningApplication`) — отдельный проход, если станет мешать.
- **Bounce × позиция** — осознанно оставлен вертикальным (`translateY`) на
  всех позициях, как в настоящем macOS Dock (боковой док там тоже прыгает
  вертикально). Амплитуда ≈ скейленный паддинг, иконка не выходит из пилюли
  ни на одной позиции ни на одном размере (проверено расчётом на 44/56/72 и
  живьём на Top/Left). На Top прыжок идёт «к краю экрана» — принято как
  цена единообразия, зафиксировано комментарием у `bounceY` в DockIcon.
- **Live-apply настроек при активном hover/magnify** — смена пресета/тумблера
  в момент наведения не сбрасывает magnify/тултип: рамка сменилась на
  статичную прямо под увеличенной иконкой, hover-состояние удержалось
  (проверено с приходом `dock-settings-changed` во время наведения).
- **Top-док и менюбар** — AppKit сам кламит always-on-top окно ниже менюбара
  (окно получает y=25 вместо 0): пилюля Top-дока полностью видима, ничего
  под менюбар не уезжает. Отдельного `visibleFrame`-кода не потребовалось.
- **Известная эргономическая заноза (не чинилось — нужен отдельный проход):**
  правый клик по 7px-разделителю при активном magnify почти всегда попадает
  в DOM-бокс увеличенного соседа (scale растит bounding box поверх слота;
  `hitTestIcon` с выбором ближайшего центра работает только для левых
  кликов через `dock-click`, а contextmenu — чистый DOM). Кликабельная
  полоска остаётся ~1–3px. Лечение — либо роутить contextmenu через тот же
  nearest-center hit-test, либо приподнимать z разделителей — меняет
  архитектуру событий, в рамках полировки не делалось.

### RGB-рамка и тонировка — через CSS custom properties, не через генерацию строк

`@keyframes rgb-glow` читает `border-color`/`box-shadow` из
`var(--dock-glow-1..6)` вместо хардкода шести цветов — сами переменные
проставляются инлайн-стилем на pill-элементе из `DockSettings.rgbGlowColors`.
Статичный цвет рамки (когда `animationsEnabled: false`) и тонировка фона
идут туда же инлайном (`color-mix(in srgb, ${color} N%, transparent)`) —
работает без дублирования разметки, потому что запущенная CSS-анимация по
спецификации всегда перекрывает инлайн-значение того же свойства: класс
`animate-rgb-glow` вешается только при `animationsEnabled`, а инлайн-цвет
всегда присутствует и просто становится видимым, когда класса нет.
