# Tauri Glass Dock — заметки из первого прохода

Конспект решений и грабель, уже пройденных при первой версии этой панели.
Не передоказывать заново — использовать как отправную точку.

## Tailwind v4: регистрация анимаций

`@theme { --animate-<name>: <keyframe-name> <duration> <easing> <iteration>; }` в
`src/index.css` сама генерирует утилиту `animate-<name>`, ровно как `--color-*`
генерирует `bg-*`/`text-*`. `@keyframes` при этом объявляются как обычно, вне блока
`@theme`. Уже сделаны и рабочие: `animate-rgb-glow` (перелив рамки), `animate-led-pulse`
(дыхание индикатора через `currentColor`, чтобы не красить фон и тень отдельно).

Числовые функциональные утилиты (`scale-*`, `opacity-*`, `rotate-*`) в v4 динамические —
`scale-120` работает из коробки, без записи в `@theme`.

## Источник иконок приложений

Для мокапа использовался проект **Dashboard Icons** (`homarr-labs/dashboard-icons`),
паттерн: `https://raw.githubusercontent.com/homarr-labs/dashboard-icons/main/png/<slug>.png`.
Важно: `cdn.jsdelivr.net/gh/homarr-labs/dashboard-icons/...` сейчас у многих иконок отдаёт
ошибку `Package size exceeded 50 MB` (репозиторий перерос лимит jsDelivr на весь GH-пакет) —
`raw.githubusercontent.com` этой проблемы не имеет, т.к. отдаёт файлы по одному.

Для реального приложения (не мокапа) удалённые PNG — временное решение. В финале лучше
доставать нативную иконку установленного приложения на диске пользователя (на macOS —
через `.icns` / `NSWorkspace`, крейт вроде `icns` или системный вызов), либо бандлить
статичный набор внутри приложения — так дизайн не зависит от сети и всегда актуальному
масштабу/DPI. Всегда оборачивать `<img>` в `onError`-fallback (бейдж с инициалами на
`app.color`) — сеть или отсутствующая иконка не должны рендерить битую картинку.

## Прозрачное окно и click-through

- Обёртка на весь экран — `pointer-events-none`; сам видимый pill дока —
  `pointer-events-auto`. Без этого прозрачное always-on-top окно перехватывает клики
  по всему нижнему краю экрана, даже там, где нет самой панели.
- CSS-уровня `pointer-events-none` достаточно для кликов внутри веб-контента, но не
  гарантированно для всех платформенных сценариев (фокус окна, drag снаружи) — держать
  в уме `appWindow.setIgnoreCursorEvents(true/false)` как второй уровень защиты,
  переключаемый по `mouseenter`/`mouseleave` на pill.
- `html, body, #root { background: transparent !important; }` — обязательная строка,
  тонет среди Tailwind preflight и легко теряется при рефакторинге `index.css`.

## Glass-эффект: backdrop-blur — это НЕ vibrancy

`backdrop-filter: blur()` блюрит контент, находящийся позади элемента в том же дереве
веб-страницы. У полностью прозрачного окна позади дока в DOM ничего нет — реальный
рабочий стол рендерится другим процессом ОС, до которого CSS не достаёт. Итог: чисто
CSS-стеклянный док на прозрачном окне НЕ блюрит то, что реально позади него на экране,
только тонирует (`bg-zinc-950/80`) без размытия.

Для настоящего frosted glass — нативный vibrancy: крейт `window-vibrancy`,
`apply_vibrancy(&window, NSVisualEffectMaterial::HudWindow, None, None)` на macOS.
Держать Tailwind `bg-zinc-950/80` как цветовой тонирующий слой ПОВЕРХ vibrancy, не
вместо него.

Подключено во втором проходе (`platform/macos.rs`, `apply_dock_vibrancy`). Материал —
`HudWindow`: это фиксированный (не семантический) материал, он остаётся тёмным
независимо от системного Light/Dark Mode — важно для always-dark Razer-Chroma эстетики.
`Sidebar` — семантический материал, в Light Mode резолвится в светлый/полупрозрачный вид
и вымывает RGB-рамку и `bg-zinc-950/80` тонировку (проверено визуально, см. коммит).

### Corner masking: окно больше пилюли — маскировать нужно blur-view, не contentView

`apply_vibrancy()` всегда растягивает свой `NSVisualEffectView` на весь `bounds()`
переданного view — то есть на весь `NSWindow` (511×111 DIP), а не на видимую CSS-пилюлю
(456×91 DIP, `rounded-[28px]`). Разница между окном и пилюлей — не случайный отступ, это
активный канвас WKWebView под RGB-glow `box-shadow` и будущий hover-magnify/tooltip
overflow (см. `PILL_TOP_RESERVE_PX` / `WINDOW_GLOW_BLEED_PX` в `constants.ts`). Поэтому
здесь нельзя просто повесить `contentView.layer.cornerRadius` + `masksToBounds` на весь
content view, как это обычно делают для frameless-окон — это заодно обрежет WebView и
сломает glow/будущий magnify overflow, а сам blur всё равно останется прямоугольным на
всю ширину/высоту окна (проверено — именно так рендерится, если этот шаг пропустить).

Рабочий рецепт: вызвать `apply_vibrancy(.., radius: Some(28.0))` как обычно (радиус тут
двигает угол ТОЛЬКО у той view, что вернёт функция), затем найти эту view обратно через
`NSView::viewWithTag` по внутреннему тегу крейта (`NS_VIEW_TAG_BLUR_VIEW = 91_376_254` —
не экспортируется, задокументировано константой с explicit-комментарием на файл/версию
крейта) и вручную сжать её `frame` до размеров пилюли (центрировано по X, с отступом
`DOCK_BOTTOM_INSET_DIP` снизу — знак смещения по Y зависит от `contentView.isFlipped()`,
проверять в рантайме, не хардкодить). `setCornerRadius` не зависит от размера — сужение
`frame` после вызова `apply_vibrancy` не портит уже выставленное скругление.

`NSRect`/`NSPoint`/`NSSize` при этом не нужно называть явно (и не нужно тащить
`objc2-foundation` отдельным доп.-зависимостью) — `content_view.bounds()` уже даёт
готовое значение нужного типа, а `origin.x/y` и `size.width/height` — публичные поля,
их можно читать/писать через инференс типа, без явного упоминания структуры.

### Click-through поллер должен знать про скруглённые углы

После маскировки поллер (`start_click_through_poller`) обязан считать «внутри пилюли» по
той же скруглённой форме, а не по прямоугольнику `pill_left/top/right/bottom` — иначе 4
угловых треугольника снаружи видимой скруглённой пилюли, но внутри её bounding box, будут
ошибочно перехватывать клики. Решение — `in_rounded_rect()`: быстрый reject по внешнему
прямоугольнику, затем проверка расстояния до центра ближайшего угла (`radius²`) только
если точка попала в угловую r×r область; в противном случае — точка на прямом крае,
сразу `true`. `radius` скейлится так же, как `pill_w`/`pill_h`/`inset` (`* scale`), т.к.
`outer_position()`/`outer_size()` у Tauri в физических пикселях, а DIP-константы — нет.

### Клики по иконкам: CGEventTap, не сэмплирование в поллере

Поллер (`start_click_through_poller`) отвечает только за непрерывное состояние:
`set_ignore_cursor_events`, `dock-hover`, `dock-cursor`. Клики — отдельный
`CGEventTap` на `LeftMouseDown` (`start_dock_click_tap`): event-driven перехват
на HID-уровне, надёжен для коротких тапов трекпада и для случаев, когда
`NSVisualEffectView` проглатывает `mouseDown` до WKWebView.

На фронте единственный обработчик toggle — `listen("dock-click")` в
`DockPanel.tsx`; у `DockIcon` нет собственного `onClick` (два источника давали
double-toggle). Tap — pass-through, событие не блокируется. Требует
Accessibility / Input Monitoring в System Settings; при неудачном создании tap
клики по иконкам не работают, hover/click-through от поллера остаются.

### Частота поллинга: sleep-бюджет, не busy-loop

`CLICK_POLL_MS` — это `std::thread::sleep` между итерациями, не busy-loop: поток спит,
затем делает несколько дешёвых вызовов (пара геттеров Tauri + позиция курсора)
и снова засыпает. Сейчас **50 ms** (20 Гц) — достаточно для границы click-through
и hover/tooltip; поднятие до 10 ms (100 Гц) — отдельное решение под будущий
hover-magnify (`dock-cursor`). Измерено на живом сборе (`ps -o pid,time` до/после,
Δ CPU time / Δ wall time): весь процесс (WebView + непрерывные CSS-анимации RGB-glow и
LED-pulse + vibrancy-композитинг + поллер) в простое — около 7% одного ядра; из них сам
поллер на 100 Гц даёт всего ~2.5 п.п. сверх бейзлайна без поллера (~4.5%, чисто
WebView-анимации) — то есть основная база CPU-нагрузки в покое не от поллера, а от
непрерывных CSS keyframe-анимаций рамки/LED, которые в любом случае работают всегда.

## LED-индикатор запущенного приложения

Цвет индикатора и его свечения берутся из ОДНОГО класса на родителе (`text-<color>-400`),
а сам индикатор использует `bg-current` (фон) и `box-shadow: currentColor` внутри
`@keyframes led-pulse` (свечение) — так не нужно синхронизировать два цвета вручную при
добавлении нового приложения в mock-данные, достаточно одного поля `color`.

## Hover-magnify в стиле macOS — отдельная фаза, не путать с обычным hover

Настоящий Dock-magnify — не `:hover { scale: 1.2 }` на одной иконке. Это непрерывная
функция расстояния курсора до КАЖДОЙ иконки в ряду (соседи тоже увеличиваются, по
затухающей кривой), пересчитываемая на каждый `mousemove`. Типичная реализация —
Framer Motion `useMotionValue` (позиция курсора) + `useTransform` на каждую иконку
(расстояние → scale), а не набор дискретных CSS-брейкпоинтов. Важно для
производительности: анимировать только `transform`/`scale` (не layout-свойства), при
необходимости троттлить `mousemove` через `requestAnimationFrame`. Планировать и
тестировать как отдельный проход поверх уже стабильной статичной геометрии панели —
не смешивать с первым проходом по вёрстке/стеклу/RGB-рамке.
